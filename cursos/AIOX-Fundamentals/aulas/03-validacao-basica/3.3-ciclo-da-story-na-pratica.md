# Ciclo da story na prática

> Resultado: conduzir uma mudança pequena do draft ao fechamento sem apagar handoffs.

## Objetivo

Sequenciar preparação, validação, implementação, QA, publicação e fechamento.

## Contexto

Story-driven development cria uma unidade persistente entre produto e código. O documento não serve para preencher formulário: ele permite que cada papel receba contexto, produza evidência e entregue ao próximo.

## Ciclo básico

    PM define epic ou direção
             ↓
    SM prepara story
             ↓
    PO valida draft
             ↓
    Dev implementa e testa
             ↓
    QA revisa e emite gate
             ↓
    Dev corrige findings, se houver
             ↓
    DevOps opera remoto, se autorizado
             ↓
    PO fecha story

Nem toda mudança exige um epic novo. O que não pode desaparecer são critérios, responsabilidade e validação.

## Skills do ciclo (core) — ordem canônica

No acervo, o SDC de **uma** story mapeia para skills `runtime-aiox`:

```text
validate-story-draft
  → develop-story
  → review-story  (+ apply-qa-fixes enquanto o gate falhar)
  → deploy-story → verify-deploy   # só se o projeto tiver deploy
  → close-story                   # única autorizada a Done
```

| Skill | Quem em geral | Artefato / gate |
|-------|----------------|-----------------|
| `validate-story-draft` | PO/SM com gate ≠ executor cego | Story Ready |
| `develop-story` | dev | código + testes locais |
| `review-story` | qa / reviewer | findings |
| `apply-qa-fixes` | dev | fixes + re-pedido de review |
| `deploy-story` | devops | versão no alvo |
| `verify-deploy` | qa/devops | prova de valor no alvo |
| `close-story` | po | Done + log |
| `full-sdc` | orquestração | corre a cadeia de **uma** story |

**Apoio:** `handoff` (passar contexto), `three-brain` / `roundtable` (review sem self-review cego), `enhance-workflow` (melhorar fluxo existente).

Detalhe e tabela expandida: [references/core-skills-runtime.md](../../references/core-skills-runtime.md).

**Erro de escala:** usar `full-sdc` em dez stories sem wave/orquestração de escopo — uma story por ciclo, ou use o mecanismo de wave do runtime/Agent Engineering.

## Condições de handoff

### SM → PO

- contexto suficiente;
- critérios observáveis;
- tarefas e file scope;
- riscos e validação;
- status de draft.

### PO → Dev

- veredito de prontidão;
- ambiguidades resolvidas;
- escopo aprovado;
- story no estado correto.

### Dev → QA

- tarefas marcadas com honestidade;
- lista de arquivos;
- comandos de validação e resultados;
- limitações conhecidas;
- nenhuma publicação remota implícita.

### QA → Dev ou DevOps

- findings priorizados;
- gate explícito;
- evidência associada;
- condição clara para correção ou avanço.

### DevOps → PO

- estado remoto;
- PR/deploy quando aplicável;
- gates executados;
- pendências ou riscos.

## Exemplo

Story: “mostrar versão do app no rodapé”.

1. SM transforma o pedido em critérios.
2. PO confirma que changelog está fora do escopo.
3. Dev implementa o valor vindo do build e adiciona teste.
4. QA verifica renderização e build.
5. DevOps cria PR somente após autorização e gate.
6. PO confirma critérios e fecha.

Se QA encontra versão hardcoded, a story volta ao dev com finding específico. O ciclo não “falhou”; o gate funcionou.

## Erro comum

Pular a validação do draft e descobrir ambiguidade durante implementação.

Outro erro é fechar a story quando o código “parece pronto”, sem registrar gate, estado remoto ou critérios atendidos.

## Prática

Use a story produzida no Módulo 2. Simule os handoffs:

1. escreva o pacote SM → PO;
2. emita um veredito PO;
3. liste o que o dev deve entregar;
4. invente um finding plausível de QA;
5. descreva a correção e a condição de fechamento.

Não implemente ainda; o objetivo é dominar o fluxo.

## Recuperação sem IA

Desenhe o ciclo e escreva uma condição de entrada e uma de saída para cada papel.

## Evidência

Uma simulação com cinco handoffs, um finding e uma condição explícita de fechamento.
