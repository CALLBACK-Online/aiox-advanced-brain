# Escolher o agent certo

> Resultado: reconhecer os 12 agents do core e encaminhar uma tarefa pelo tipo de responsabilidade.

## Objetivo

Relacionar trabalho, autoridade e evidência ao agent correto, sem escolher por nome aproximado ou preferência pessoal.

## Contexto

Agents não são “personalidades diferentes para o mesmo chat”. Cada definição combina especialidade, limites, comandos e handoffs. A pergunta certa não é “de qual gosto mais?”, mas “quem possui esta decisão e qual artefato deve sair?”.

## Skills de persona no acervo (`runtime-aiox`)

No repositório de distribuição, cada orbital tem skill espelho em `skills/aiox-*/SKILL.md` (exceto o master que também aparece como `aiox-master`). Exemplos:

| Agent | Skill no acervo |
|-------|-----------------|
| analyst | `skills/aiox-analyst/SKILL.md` |
| pm | `skills/aiox-pm/SKILL.md` |
| architect | `skills/aiox-architect/SKILL.md` |
| ux-design-expert | `skills/aiox-ux-designer/SKILL.md` |
| data-engineer | `skills/aiox-data-engineer/SKILL.md` |
| sm | `skills/aiox-sm/SKILL.md` |
| po | `skills/aiox-po/SKILL.md` |
| dev | `skills/aiox-dev/SKILL.md` |
| qa | `skills/aiox-qa/SKILL.md` |
| devops | `skills/aiox-devops/SKILL.md` |
| aiox-master | `skills/aiox-master/SKILL.md` |

**Como usar de verdade**

1. Escolha o agent pela **autoridade** (tabela acima).
2. No projeto destino, copie a skill se o runtime for skill-first.
3. Se o runtime só conhece `@dev`, use o agent; a skill documenta o mesmo papel.
4. Detalhamento expandido: [references/core-skills-runtime.md](../../references/core-skills-runtime.md).
5. Inventário de todas as skills do acervo (incluindo as que **não** são core): abra no explorer `cursos/MAPA-SKILLS.md`.

Não confunda skill de **persona** com skill de **entrada de squad** (ex. `research`, `etl-ops`). Squads têm aula 1:1 em `cursos/AIOX-Advanced-Squads/`.

## Heurística de seleção

1. Nomeie o substantivo principal do trabalho: pesquisa, PRD, arquitetura, dados, story, código, qualidade ou operação remota.
2. Identifique a decisão exclusiva: quem pode aprovar, migrar, fechar ou publicar?
3. Defina o artefato esperado.
4. Escolha o agent responsável.
5. Registre o próximo handoff.

## Exemplo

“Precisamos adicionar cobrança recorrente.”

Isso não é uma única delegação:

- analyst pesquisa restrições e alternativas, se necessário;
- PM define requisitos e escopo;
- architect decide integração;
- data-engineer trata dados e migrações;
- SM prepara stories;
- PO valida;
- dev implementa;
- QA revisa;
- devops publica quando autorizado.

Para uma correção pequena, a cadeia será menor. O mapa não obriga usar todos os agents.

## Erro comum

Enviar “faça tudo” ao aiox-master. O master deve rotear responsabilidades especializadas; não apagar a autoridade dos especialistas.

Outro erro é pedir push ao dev ou implementação ao QA. Capacidade técnica não equivale a autoridade operacional.

## Prática

Roteie estes cenários:

1. comparar três APIs;
2. escrever PRD;
3. desenhar schema e RLS;
4. preparar uma story;
5. implementar a story;
6. criar PR após gates;
7. revisar acessibilidade;
8. criar um squad novo.

Para cada um, escreva agent, artefato e próximo handoff.

## Recuperação sem IA

Desenhe de memória quatro grupos: descoberta, planejamento, entrega e meta. Distribua os 12 agents entre eles.

## Evidência

Oito cenários roteados sem conflito de autoridade, cada um com artefato esperado.
